hashira: the pillars every release stands on.

Reusable GitHub Actions workflows and composite actions for the three shapes most projects ship: an npm package, a NuGet package and a static site on Pages. Pinned, least-privilege, and publishing through OIDC, so a release needs one approval and no long-lived token.

Flows

Three shapes, one contract

Each flow is a CI reusable workflow plus a release composite action. Your repo keeps one or two short caller files.

npm-package-ci · npm-release

npm package

Lint, test and scan on every PR. Release on a dispatch with a bump: pack, publish with OIDC trusted publishing, tag and GitHub Release.

nuget-package-ci · nuget-push

NuGet package

Build, test and pack with the resolved version stamped in, then push to nuget.org through OIDC, behind one production approval.

static-webapp-ci · pages-deploy

Static site

Build, test, scan and upload in one job, then deploy to GitHub Pages from main only, with a guard that refuses pull-request events.

Use it

A caller file is a few lines

jobs:
  ci:
    uses: skathio/hashira/.github/workflows/npm-package-ci.yml@v2
    permissions:
      contents: read
      pull-requests: write
      security-events: write
    with:
      library_ref: 'v2'   # the same ref as the uses: pin

Pin to a full commit SHA for reproducible builds, or to v2 for the rolling major. Never main.

Security

What it carries for you

Pinned actionsEvery third-party action is pinned to a full commit SHA, with its version in a comment.
Deny-all permissionsThe workflow baseline is {}; each job is granted only what it needs.
OIDC publishingTrusted publishing to npm and nuget.org. No token to leak or rotate.
Explicit releasesA dispatch with a bump picks the version. Nothing is inferred from commit messages.
Scan suiteosv, gitleaks, dependency review, CodeQL and actionlint. Each flow sets its defaults, and you can switch any of them off.
No pull_request_targetShape lints refuse the trigger that hands secrets to fork PRs.
