# npm package flow — adoption walk-through

> **Audience**: a consumer adopting `skathio/hashira` for an npm package repo.
> **Scope**: copy-paste-ready CI + Publish caller workflow templates, input
> tables, OIDC trusted-publisher onboarding, `production` Environment setup,
> common failure modes.
> **Status**: derived directly from `.github/workflows/npm-package-ci.yml`
> and `.github/actions/npm-release/action.yml` (v2 shape, `semantic-release`
> removed entirely — see "What changed from v1" below). The real,
> end-to-end-validated publish (`@skathio/somi-ai@0.2.0`, 2026-06-01) ran
> under v1's `semantic-release`-based composite; v2's explicit-version path
> has not yet had a live validation release (that's Phase 6 of this work
> item) — every OIDC mechanism described below is otherwise unchanged from
> what that release validated (the npm CLI's own native OIDC exchange, not
> something v2 introduces).

For cross-cutting concepts (pin policy, gate model, secret-passing model,
permissions baseline, OIDC trust onboarding narrative, the versioning model
end-to-end), see [`../usage.md`](../usage.md).

## What changed from v1

v1's `npm-release` composite ran `semantic-release` end-to-end: it computed
its own version from conventional-commit history, then published via
`@semantic-release/npm` and tagged/released via `@semantic-release/github`.
**v2 removes `semantic-release` and all four of its plugins entirely.** The
version is now resolved once, in CI, by the `version-resolver` composite
action (D1/D8) — `npm-release` only *consumes* the already-resolved version
as a required input; it does not compute or stamp one. See
[`../usage.md`](../usage.md#versioning-model) for the full versioning
narrative, including D14's seed-plus-bump-on-top semantics.

Concretely, this means: no more conventional-commit discipline gating
whether a release happens at all; no more "no relevant changes" silent
no-ops; the resolved version is surfaced in the run summary *before* the
build step (NFR-DX-3); and Release notes now come from GitHub's own
`--generate-notes` heuristic (D13) rather than semantic-release's
commit-message parsing.

### Release-notes content change (D13)

This is a behavior change worth calling out on its own, not just a
mechanism swap: v1's Release notes were generated by
`@semantic-release/release-notes-generator`, which parses **conventional-commit
messages** in the commit range since the last release. v2's
`gh release create --generate-notes` instead uses **GitHub's own
server-side PR/commit-range heuristic**, which summarizes from **merged-PR
titles and labels**. If your repo's PR titles aren't curated the way your
commit messages were, expect the notes to look meaningfully different — not
necessarily worse, just generated by a different signal. This requires no
new resolver output (D8's one-scalar `version` output is untouched); it is
purely a CD-composite-side flag change. See
[`../usage.md`](../usage.md#release-notes) for the cross-cutting framing.

## 1. CI caller workflow template

Copy this into `.github/workflows/ci.yml` in your npm package repo:

```yaml
# .github/workflows/ci.yml
name: ci
on:
  pull_request:
  push:
    branches: [main]
  workflow_dispatch:
    inputs:
      bump:
        description: "Set to cut a release: patch | minor | major. Leave empty for a routine CI run."
        type: choice
        options: ['', patch, minor, major]
        default: ''
      seed_version:
        description: "Bare semver baseline (e.g. '0.0.0'). Only needed for the first release / no prior stable tag."
        type: string
        default: ''

# Deny-all default; each job grants what it needs.
permissions: {}

jobs:
  ci:
    # Pin to a SHA for reproducible builds (recommended), or @v2 for the
    # rolling tag. NEVER pin to @main — see docs/usage.md "Pin policy".
    uses: skathio/hashira/.github/workflows/npm-package-ci.yml@<40-char-sha>
    # Per-job grants MUST mirror the matrix below — reusable workflows
    # can only narrow the caller's grants, not broaden them.
    permissions:
      contents: read
      pull-requests: write       # commitlint sticky comment + coverage report
      security-events: write     # CodeQL (when scan_disable enables it)
    with:
      node_version: '20'
      test_command: 'npm test'
      coverage_path: 'coverage/lcov.info'
      # scan_disable defaults to 'codeql,actionlint'. Pass '' to enable
      # everything; pass a CSV to disable specific scans.
      # scan_disable: ''
      library_ref: '<40-char-sha>'  # MUST be the SAME SHA as @<…> above.
      bump: ${{ inputs.bump }}
      seed_version: ${{ inputs.seed_version }}
```

`bump`/`seed_version` are passed straight through to the CI workflow's
`version` job, which only runs when `bump` is non-empty (every routine
PR/push run leaves it empty and is unaffected). The maintainer triggers a
release via `gh workflow run ci.yml -f bump=minor` (or the Actions UI's "Run
workflow" form).

## 2. Publish caller workflow template

The publish step is a **composite action (`npm-release`) called from a job
in your own `ci.yml`** — NOT a reusable workflow. This is required: npm
OIDC trusted publishing validates the OIDC token's `job_workflow_ref` claim
against the trusted-publisher's registered "Workflow filename," and a job
running inside a `workflow_call`-invoked reusable workflow carries the
*reusable workflow's* path as that claim — which can never match your
`ci.yml`. A composite action runs inline in *your* job's context, so
the claim matches and OIDC works (D2's architectural spine — see
[`../usage.md`](../usage.md#gate-model)).

Because the gated `publish` job lives in the **same caller file** as `ci`
(linked via `needs:`), the CD job reads the resolved version straight off
the CI job's output — `needs.<job-id>.outputs.resolved_version` — there is
nothing to recompute. Do **not** wire this as a separate `workflow_run`-
triggered file — that is exactly the cross-run secret-exposure shape v2
avoids (see [`../usage.md`](../usage.md#not-workflow_run)). Append this job
to the same `ci.yml` file from §1:

```yaml
# .github/workflows/ci.yml (continued — same file as §1)
  publish:
    needs: ci
    if: ${{ inputs.bump != '' }}
    runs-on: ubuntu-latest
    environment: production   # single gate; configure >=1 required reviewer (see §7)
    permissions:
      id-token: write       # npm OIDC trusted-publishing token exchange (auth: oidc/auto)
      contents: write        # gh release create tags the commit
      pull-requests: read    # --generate-notes reads merged-PR metadata (read-only)
    steps:
      - uses: actions/checkout@<sha>  # v4.2.2
        with:
          persist-credentials: true  # REQUIRED: gh release create needs git
                                      # credentials on this job. checkout's default,
                                      # but set it explicitly — a consumer who
                                      # hardens with persist-credentials:false gets
                                      # a SILENT tag/release failure AFTER publish.
      - uses: skathio/hashira/.github/actions/npm-release@<40-char-sha-or-v2>
        with:
          version: ${{ needs.ci.outputs.resolved_version }}  # D8 — consumed, not recomputed
          # auth defaults to 'auto'. Use 'oidc' once trusted publishing is
          # confirmed working (no silent downgrade); 'token' to opt out of
          # OIDC entirely.
          # auth: oidc
          # Only if auth=token, or as the auth=auto fallback. This is a
          # declared composite-action INPUT (with:), not an env var —
          # npm-release never reads secrets.*/env.* for the token, only
          # inputs.npm_token.
          # npm_token: ${{ secrets.NPM_TOKEN }}
```

The `ci` job (§1) is the gate: `publish` only runs after it passes, and only
when `bump` was set on the dispatch. One `production` approval per release.

## 3. Input table

Every input across the `npm-package-ci.yml` reusable workflow and the
`npm-release` composite action, with type, default, and meaning — verified
field-by-field against the actual shipped YAML.

### CI inputs (`npm-package-ci.yml`)

| Input | Type | Default | Meaning |
|-------|------|---------|---------|
| `node_version` | string | `"20"` | Node major to install via `actions/setup-node` before lint/test/scan/coverage. |
| `test_command` | string | `"npm test"` | Shell command that runs the consumer's tests. **Trusted input (raw-shell sink per D10d)** — do NOT pass values derived from PR titles, issue bodies, branch names, or other externally controlled context. |
| `coverage_path` | string | `"coverage/lcov.info"` | Path to the lcov coverage file produced by `test_command`. Consumed by `coverage-report`. |
| `scan_disable` | string | `"codeql,actionlint"` | Comma-separated list of scans to skip (D10c). Pass `""` to enable everything. Values: `codeql`, `osv`, `gitleaks`, `dependency-review`, `actionlint`. |
| `library_ref` | string | _(required, no default)_ | SHA, tag, or branch of `skathio/hashira` checked out into `.hashira/` for in-repo composite actions (D9/D14). **Required** — every caller must pin it explicitly. PIN TO A SHA for reproducible builds; see the dual-pin invariant in [`../usage.md`](../usage.md#the-library_ref-dual-pin-invariant). |
| `bump` | string | `""` | One of `patch`\|`minor`\|`major`. Optional — leave empty for routine PR/push CI runs that aren't cutting a release. When set, the `version` job resolves the next version, surfaces it in the run summary, and stamps it into a packed tarball (D1/D8). |
| `seed_version` | string | `""` | Bare semver baseline (e.g. `"0.0.0"`) for a major/initial release with no prior stable tag (FR-3). Passed through to `version-resolver` unchanged; ignored when a stable tag already exists or `bump` is empty. D14: the chosen `bump` still applies arithmetic **on top of** the seed — it is not published literally. |

### CI output (`npm-package-ci.yml`)

| Output | Meaning |
|--------|---------|
| `resolved_version` | The resolved, validated bare semver string (e.g. `"1.3.0"`, no `v` prefix). Empty when `bump` was not provided. The workflow's **only** output (D8) — there is no second output for the `v`-prefixed tag form (derive it yourself: `v${{ needs.ci.outputs.resolved_version }}`) or for the bump kind (already your own dispatch input). |

### Publish inputs (`npm-release` composite action)

| Input | Type | Default | Meaning |
|-------|------|---------|---------|
| `version` | string | _(required)_ | The resolved, validated bare semver string (e.g. `"1.3.0"`) to publish-tag-and-release. Consumed as-is from the CI workflow's `resolved_version` output (D8) — this action does not compute or re-derive a version. Re-validated against strict semver here as the action's own checkpoint-2 (B7). |
| `node_version` | string | `"24"` | Node version for `actions/setup-node` (LTS; ships npm ≥ 11.5.1, satisfies npm's own OIDC Node floor). The action fail-fasts on Node < 22.14 or npm < 11.5.1. Trusted input. |
| `target` | string | `"https://registry.npmjs.org"` | Registry URL to publish to. OIDC trusted publishing engages only for the official registry; other registries use token auth. Trusted input. |
| `auth` | string | `"auto"` | `oidc` \| `token` \| `auto` (D3/D11). See "Auth model" in §6. Trusted input. |
| `npm_token` | string | `""` | npm registry token. Pass via a **`with:` input** sourced from `secrets:` in the caller — **not** an `env:` var; `npm-release` never reads `secrets.*`/`env.*` directly, only `inputs.npm_token` (composite actions have no `secrets:` context). Required (and used directly) when `auth=token`; usable as the `auto` fallback; ignored when `auth=oidc`. |
| `working_directory` | string | `"."` | Directory to run `gh release create` from (must be the consumer's checked-out repo). Trusted input. |

### Publish outputs (`npm-release`)

| Output | Meaning |
|--------|---------|
| `released` | `"true"` if a publish was performed this run, else `"false"` (dry-run only — the reserved `HASHIRA_NPM_RELEASE_DRY_RUN` test hook; consumers must never set this in production). |
| `version` | The published version (echo of the `version` input) when `released=='true'`, else empty. |

There is no `x_releaserc_overrides`-style experimental input in v2 — that
input was part of the now-deleted semantic-release integration and has no
v2 equivalent.

## 4. Secret table

| Secret | Required | Where | Purpose | OIDC obviates? |
|--------|----------|-------|---------|-----------------|
| `NPM_TOKEN` (your name; passed as the `npm_token` `with:` input) | optional | consumer's `publish` job, passed via `with: npm_token: ${{ secrets.NPM_TOKEN }}` | Long-lived npm publish token (fallback / non-official registries / `auth: token`). | Yes on the official registry under `auth: oidc`/`auto` — npm's own CLI (≥ 11.5.1) performs **native OIDC trusted publishing**, no token needed. Pass `npm_token` only for a custom registry, `auth: token`, or as the `auto` fallback. |

The `npm-release` action sources the GitHub token from `${{ github.token }}`
itself via an `env: GITHUB_TOKEN: ...` block (composite actions have no
`secrets:` context to read from directly) — you do not pass it. The CI half
needs no secrets at all.

## 5. Permissions table

Per-job grants the consumer's workflows MUST set, verified field-by-field
against the actual `permissions:` blocks in `npm-package-ci.yml` and the
caller-job contract documented in `npm-release/action.yml`'s header.
Reusable workflows (the CI half) can only NARROW the caller's grants, so the
consumer mirrors them at the caller job; the `npm-release` composite action
cannot declare its own `permissions:` at all (no GitHub Actions primitive
for that on a composite action) — the grant lives entirely on the
**consumer's own job** that invokes it.

### CI permissions

| Caller job calls | `contents` | `pull-requests` | `security-events` | Why |
|-------------------|------------|------------------|---------------------|-----|
| `npm-package-ci.yml` | `read` | `write` | `write` | `pull-requests:write` for the commitlint sticky comment (D11) + coverage-report sticky comment. `security-events:write` for CodeQL when enabled via `scan_disable`. `contents:read` for checkout. The `version` job (when `bump` is set) needs only `contents: read` — it never writes to the working tree (D1 stamp-only). |

### Publish permissions

Set these on the consumer's `publish` job (the one that calls
`npm-release`):

| Job | `contents` | `pull-requests` | `id-token` | Why |
|-----|------------|------------------|------------|-----|
| `publish` (calls `npm-release`) | `write` | `read` | `write` | `id-token:write` for OIDC trusted-publishing token exchange (`auth: oidc`/`auto`). `contents:write` for `gh release create`'s tag + Release creation. `pull-requests:read` because `--generate-notes` (D13) only **reads** merged-PR metadata to compose notes — it does not write to or comment on PRs. |

There is no `issues: write` grant in v2 — that was v1's
`@semantic-release/github` failure-issue plugin, removed entirely. The
consumer's workflow-level `permissions: {}` (deny-all) is recommended; the
per-job grants above are the minimum required. Granting more at workflow
level inflates the `GITHUB_TOKEN`'s blast radius across every job in the
file.

## 6. OIDC trusted-publisher onboarding (npm)

> The OIDC token exchange + provenance attestation mechanism below was
> validated end-to-end against a real publish (`@skathio/somi-ai@0.2.0`,
> 2026-06-01) under v1's composite. v2 keeps this mechanism completely
> unchanged — the npm CLI on `PATH` still performs the exchange natively;
> what changed is only *what calls* `npm publish` (a direct call now,
> instead of `@semantic-release/npm`'s plugin function).

OIDC trusted publishing eliminates long-lived `NPM_TOKEN` secrets by
exchanging a short-lived GitHub OIDC token for a publish token at publish
time. The npm CLI on `PATH` does this **natively** — no plugin, no separate
login step. `npm-release` does not call any login step itself.

> **Toolchain floor (load-bearing):** the publish runs `npm publish` via the
> **PATH npm CLI**, which must be ≥ 11.5.1 — required by npm's own OIDC
> trusted-publishing feature itself (npm's official docs). `npm-release`
> defaults to Node 24 (ships npm 11.13.0) and upgrades npm automatically if
> the runner's is older; it fails fast if Node itself is < 22.14 (also
> required by npm's OIDC feature).

### Auth model — `auth: oidc | token | auto`

There is no silent downgrade from the secure path (D3/D11):

- **`auth: oidc`** — always attempt native OIDC. On failure, **fails
  loud** — never falls back to `npm_token`, even if one is set. The secure,
  recommended setting once trusted publishing is confirmed working.
- **`auth: token`** — always use `npm_token` directly; OIDC is never
  attempted. An explicit opt-out.
- **`auth: auto`** *(default)* — attempt OIDC first; on failure, if
  `npm_token` is present, fall back to it with an `::warning::` annotation.
  If OIDC fails and no token is present, fails loud, same as `auth: oidc`.

Mechanism: npm's own `oidc()` function is designed to **never throw** on
failure — it silently falls through to whatever credential it finds via
`.npmrc`/env. `npm-release` cannot get "OIDC never silently falls back" by
observing an outcome (there's no separate login step to observe, unlike
NuGet's `NuGet/login`); instead it enforces `auth` via **environment
hygiene** on the `npm publish` subprocess: under `auth: oidc`, the publish
subprocess runs from a throwaway, empty working directory (so no project
`.npmrc` is found on the cwd/ancestor walk) and every credential npm could
fall back to is positively scrubbed from its environment
(`NPM_TOKEN`/`NODE_AUTH_TOKEN` unset, every `npm_config_*`/`NPM_CONFIG_*` var
cleared from the actual environment, and a throwaway empty
`--userconfig`/`--globalconfig`). With genuinely zero reachable
credentials, a real OIDC failure surfaces as npm's own `ENEEDAUTH` —
fail-loud **by construction**, not by branching on an observed result. The
`auth: token` path applies the identical clean-cwd + scrub treatment (minus
the OIDC env vars, which are deliberately unset instead) so the consumer's
intended `npm_token` is provably the credential that gets used, not silently
shadowed by a project `.npmrc` or a stray `npm_config_*` var.

Setup (one-time, on npmjs.com):

1. Sign in to <https://www.npmjs.com> and open the package page:
   `npmjs.com/package/<package-name>`.
2. Click **Settings** → **Publishing access** → **Automated publishing**.
3. Add a trusted publisher with these values:
   - **GitHub organization or user**: `<your-github-org-or-user>`
   - **Repository name**: `<your-package-repo-name>`
   - **Workflow filename**: `ci.yml` (matches the file you created in §1/§2
     — CI and the gated `publish` job live in the same caller file)
   - **Environment name** (optional but recommended): `production` (matches
     the `environment:` on your `publish` job)
4. Save the trusted publisher configuration.

**Verification**:

- The real `publish` job's `npm publish` call triggers the OIDC token
  exchange; if the trusted-publisher config doesn't match
  (org/repo/workflow-filename/environment), the npm registry returns **401**
  at the publish step.
- Provenance (`--provenance`) is passed automatically on the clean OIDC-only
  attempt (`auth: oidc` always, `auth: auto`'s first attempt) — it is
  **conditional**, not unconditional: npm's own provenance-prerequisite
  check throws under `auth: token`'s deliberately-scrubbed environment, so
  `--provenance` is correctly omitted there. With OIDC + provenance active,
  the published package carries a signed provenance attestation
  (`predicateType https://slsa.dev/provenance/v1`) logged to the sigstore
  transparency log, linking it to the GitHub Actions run.

**Precedence when both `npm_token` and OIDC are configured** (`auth: auto`):
the clean OIDC-only attempt always runs first; `npm_token` is only consulted
if that attempt fails. Recommended: do NOT pass `npm_token` once OIDC is
working — leaving it set can mask a misconfigured trusted-publisher during
onboarding, and the recommendation is to move to `auth: oidc` once
confirmed, rather than leaving `auto` as a permanent steady state.

## 7. `production` Environment setup checklist

The `publish` job in your caller workflow declares `environment: production`.
That key IS the gate — configure the Environment BEFORE the first publish
run, otherwise the job proceeds without pausing.

1. In your package repo, open **Settings** → **Environments** → **New
   environment**.
2. Name it `production` (match the `environment:` on your `publish` job and
   the npm trusted-publisher's "Environment name").
3. Under **Deployment protection rules**, enable **Required reviewers** and
   add at least one reviewer (yourself, or your team).
4. Optionally restrict the **Deployment branches** to `main`.
5. Save.

**Verification**: trigger a release (`gh workflow run ci.yml -f bump=patch`).
The `publish` job should pause with "Waiting for review" — click **Review
deployments** → **Approve and deploy**.

> Note: with `prevent_self_review` left at its default (off), GitHub
> auto-approves a deployment for the user who *triggered* the run, so a
> maintainer who dispatches the release themselves won't see a pause. That's
> one approval per release by design; enable `prevent_self_review` if you
> require a second person.

### One-time `gh api` setup: require a reviewer (D12)

The library **cannot** runtime-verify that your `production` Environment has
a required reviewer configured — the `gh api environments` endpoint needs
admin-tier scope the workflow's `GITHUB_TOKEN` doesn't carry. Run this once,
with your own admin-scoped credentials, instead of (or in addition to) the
manual UI steps above:

```bash
# Require at least one reviewer on the `production` Environment before the
# first publish run. Replace OWNER/REPO and the numeric reviewer id (look it
# up via `gh api users/<username>`).
gh api --method PUT \
  repos/OWNER/REPO/environments/production \
  -f wait_timer=0 \
  -F "reviewers[][type]=User" \
  -F "reviewers[][id]=<numeric-user-id>" \
  -F deployment_branch_policy='{"protected_branches":true,"custom_branch_policies":false}'
```

A misconfigured Environment (zero reviewers) runs the gated job immediately
without pausing, and this is silent and indistinguishable from working until
something bad publishes — see [`../usage.md`](../usage.md#environment-reviewer-gate--what-the-library-can-and-cannot-verify)
for the full defense-in-depth story (this snippet + a self-CI lint asserting
the gated job declares `environment:`).

## 8. Release walk-through

The whole release happens in **one workflow run**, across two jobs in the
same caller file (`ci` → `publish`, linked via `needs:`):

1. A maintainer dispatches `ci.yml` with `bump` set (e.g. `minor`).
2. The `version` job (inside `npm-package-ci.yml`) resolves the next
   version from tag history, surfaces it in the run summary, stamps it into
   an isolated-copy `package.json`, packs the tarball, and uploads it as the
   `npm-tarball` artifact (D1/D8 — see [`../usage.md`](../usage.md#versioning-model)).
3. Once `ci` succeeds and the `production` Environment is approved, the
   `publish` job downloads that exact tarball (never re-packed), publishes
   it via `npm publish` under the chosen `auth` mode, then — only after a
   successful publish — creates the `v<version>` tag and GitHub Release
   (`--generate-notes`).

**Tag-driven, no commit-back**: `package.json` is never committed back to
the branch — the resolved version exists only in the packed artifact and the
git tag. The in-repo `package.json` stays at whatever version it had before
the release (D1's stamp-only invariant, preserved unchanged from v1's
`npm-publish-redesign` decision). The point of no return is `npm publish`
(npm unpublish has a 72-hour window with caveats; recovery is "publish a
higher version with the fix").

**Atomicity — tag/Release creation happens only after a successful
publish**: the `npm publish` step is attempted first; on failure, the
composite halts and **no tag or Release is created** (FR-8's safe-re-run
requirement — see [`../usage.md`](../usage.md#atomicity--tagrelease-creation-happens-only-after-a-successful-publish)).
Only after a successful publish does the tag/Release step run, and it is
idempotent (`gh release view` first) — re-running the gated job after a
partial earlier failure does not fail on an already-existing tag/Release.
**There is no npm equivalent of `--skip-duplicate`** (NuGet's
`dotnet nuget push` has one; npm does not) — if the publish step itself
partially succeeded against the registry but the workflow run failed before
recording it, a re-run's `npm publish` will fail with the registry's own
"cannot publish over previously published version" error rather than
exiting cleanly. This is a documented gap, not a hidden one: recover by
bumping to the next version, or by manually confirming via
`npm view <package> versions` whether the prior attempt actually published
before re-running.

### Release notes (D13)

`npm publish`'s tag/Release step passes `--generate-notes` to
`gh release create` — GitHub's own server-side PR/commit-range heuristic
populates the Release body. **Expect a content-character change** from v1:
semantic-release parsed conventional-commit messages; `--generate-notes`
summarizes from merged-PR titles/labels instead. If your repo's PR titles
aren't curated, the notes will look different — not necessarily worse, just
generated by a different heuristic. See "What changed from v1" above and
[`../usage.md`](../usage.md#release-notes) for the cross-cutting framing.

## 9. Common failure modes

- **`npm publish` fails with the registry's "cannot publish over previously
  published version" error on a re-run.** No `--skip-duplicate` equivalent
  exists for npm (see "Atomicity" above) — a partial prior attempt that
  actually reached the registry leaves no clean idempotent retry path.
  Check `npm view <package> versions` to confirm whether the version already
  shipped before re-running with a bumped version.

- **npm trusted-publisher misconfigured → 401 on the publish step**. The
  OIDC token exchange succeeds (GitHub side) but the registry rejects the
  publish because the trusted-publisher record doesn't match
  org/repo/workflow-filename/environment. Re-check §6's fields against your
  actual caller workflow's filename + the `environment:` on the `publish`
  job.

- **Missing `id-token: write` on the `publish` job → publish fails with
  `ENEEDAUTH`**. On the official registry with `auth: oidc` (or `auto` with
  no `npm_token`), the OIDC token request fails and npm has no credential at
  all → npm's own `ENEEDAUTH` at the publish step. Fix: grant
  `id-token: write` (it's in the §2 template).

- **`persist-credentials: false` (or omitted) on checkout → tag/Release
  creation fails after a successful publish**. `gh release create` needs
  git credentials on the `publish` job (the composite's tag/Release step
  runs `gh` against the checked-out repo). Use `persist-credentials: true`
  (in the §2 template) — the publish itself can succeed while the
  tag/Release step fails silently afterward if this is missing.

- **Node < 22.14 or npm < 11.5.1 → action fails fast on the OIDC floor
  check**. `npm-release` enforces both floors (the PATH npm performs the
  OIDC exchange). Use `node_version: '24'` (the default).

- **`npm_token` set AND OIDC working (`auth: auto`) → masks misconfig**. On
  the official registry, OIDC is attempted first and the token is only a
  fallback; leaving it set can hide a broken trusted-publisher during
  onboarding. Omit `npm_token` once OIDC works, or move to `auth: oidc`
  explicitly (no fallback at all).

- **`auth: oidc` failure has no fallback by design — re-check trust-publisher
  config rather than adding a token.** This is intentional (D3/D11):
  `auth: oidc` never falls back to `npm_token`, even if one is set. If the
  real intent is "use OIDC, but tolerate a misconfiguration with a warning,"
  switch to `auth: auto` rather than wiring a token alongside `oidc`.

- **No `version` job ran — `resolved_version` output is empty.** The `ci`
  job's `version` job is gated on `inputs.bump != ''`. If you dispatched
  without setting `bump`, the job is skipped entirely (correct behavior for
  a routine PR/push run) and the `publish` job's `if: ${{ inputs.bump != ''
  }}` guard also skips. Re-dispatch with `bump` set to cut a release.
